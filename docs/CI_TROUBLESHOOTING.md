# Container runtime readiness failures

The runtime job checks both Docker's in-container health and a certificate-verified connection from the runner through the published localhost port. The test bridge must permit runner ingress; scripts/runtime-network.sh rejects new external egress while preserving runner replies and traffic within the test bridge. Never replace it with an internal-only bridge: in-container health can pass while the runner cannot reach the published port.

The current readiness helper returns errors to the calling subtest instead of calling FailNow on a captured parent test. It bounds probes and retries with one context. Failure output includes the last TCP/TLS/HTTP health error, probe count, source revision, Compose state, port binding, the in-container probe result and recent proxy logs. The workflow uploads reports/readiness-failure.txt and source hashes with runtime evidence. No secret files or container environment are printed.

If you see the old message `runtime_test.go:90: proxy did not recover` followed by `subtest may have called FailNow on a parent test`, check the run's commit. That signature predates the corrected helper and network configuration. GitHub's **Re-run jobs** repeats the original workflow commit; it does not pick up main's fixes. Use Actions → CI → Run workflow → main, or inspect the newest main push run. The current run summary and first runtime-test log identify the exact tested revision and readiness_version=2. The container suite runs twice to check recovery on an already-restarted stack.

For a current failure, inspect the actual last error: connection refused suggests an exited process or missing publication; TLS trust/hostname failure suggests CA/certificate mismatch; 407 suggests mismatched operator credentials; in-container health succeeding with a failed host probe suggests bridge/firewall/publication configuration. Fix the underlying problem rather than extending the 45-second timeout or removing authentication/TLS checks.
